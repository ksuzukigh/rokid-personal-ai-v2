# 私のAI V2

**Macで相談していた仕事の続きを、眼鏡から声で進める。**

「私のAI」は、マイクとディスプレイを備えたRokidのスマートグラスから、MacのAIへ話しかける、鈴木啓一の個人開発プロジェクトです。

このページは、一般事務職の方をはじめ、プログラミングに詳しくない方に向けて書いています。何に役立つのか、どう使うのか、なぜ作ったのかを紹介します。自分でも似た仕組みを作りたい方へ、AIや開発を手伝う人と相談するための資料も用意しました。

## まずここだけ読む

### どんなことに役立つのか

Macで資料を調べたり、文書の下書きをAIと相談したりしていると、席を離れてから追加の考えが浮かぶことがあります。「さっきの資料に、この点も入れたい」と眼鏡へ話しかけて、その相談を続けられるようにしました。

AIが確認したいことを聞いてきたら、声で答えます。途中経過や返事は眼鏡に表示されます。机に戻ったら、同じMacの会話を開いて、資料を見ながら作業を続けられます。

**V2で大切にしたのは、眼鏡とMacで同じ相談の続きを進められることです。** この個人環境では、調査や文書作成を手伝うAIアプリ「Codex」をMacで使っています。

### どう使うのか

1. 眼鏡で「私のAI」を開き、「タップして話す」を1回操作して話します。
2. 話し終えたら、もう1回操作して録音を終えます。
3. 別の相談の続きを始めるときや、新しい相談を作るときは、画面の会話名を確認します。
4. AIの返事を読みます。続けるときは「タップして続けて話す」を1回操作して話します。

アプリを開いただけでは録音しません。文書を保存・編集する前には、対象と内容を示して確認を受ける設計です。

### V1から何が変わったのか

V1でも、眼鏡からAIとの会話、調査、確認後の文書保存ができました。V2では、**Macで普段使っている会話を選び、その相談や作業を続けること**を中心にしました。これまでのやり取りや、Macで利用できる資料・道具を使って進めます。

### 利用には何が必要か

作者が確認したのは、Rokid AI Glasses RV101とMacを使う個人環境です。利用中はMacが起動してログインしており、眼鏡とMacが必要な通信をできる状態にしておきます。外出先では眼鏡をスマートフォンのテザリングなどでインターネットにつなぎます。

**この公開ページで提供するのは、考え方と作るための参考資料です。** 完成したアプリやインストーラーは配布していません。似た仕組みを作るには、自分の環境に合わせた開発と確認が必要です。

眼鏡の小さな画面では長い文書を確認しづらいため、詳しい確認や仕上げにはMacも使います。ほかの人の環境で同じように動くことは、まだ確認していません。

## 会話と操作の例

資料を調べたり、文書の下書きを考えたりする場面での使い方を紹介します。以下の会話は、体験を説明するための架空の例です。実際の発言の転載や、この言葉どおりに動くことの保証ではありません。

### 最初の操作

眼鏡で「私のAI」を開きます。「タップして話す」を1回操作すると録音が始まります。話し終えたら、もう1回操作して録音を終えます。

AIの返事を読んで続けるときは、「タップして続けて話す」を1回操作します。前の会話がすでに表示されている場合も、この表示から話し始めます。アプリを開いただけでは録音しません。

### 文書の下書きの相談を続ける

Macで説明資料の構成を相談してから、席を離れた場面です。

> 私：さっきの説明資料の相談を続けたい。初めて読む人向けの説明も入れたい。
>
> AI：説明資料の相談の続きを、この会話で進めますか？
>
> 続ける会話：業務改善の説明資料
>
> 私：はい、その会話です。
>
> AI：初めて読む人が、どこで困りそうかを考えましょう。どんな業務を説明する資料ですか？

画面の会話名を見て、続けたい相談か確認します。AIは、その会話のこれまでのやり取りを踏まえて進めます。普通の続きの発言では、会話先を毎回確認し直しません。

机に戻ったら、同じMacの会話を開きます。眼鏡から話した内容も含めて、下書きの続きを進められます。

### 新しい相談を始める

> 私：新しい相談で、資料を探す手間を減らす方法を考えたい。
>
> AI：新しい会話を始めますか？
>
> 新しく始める会話：資料を探す手間の見直し
>
> 私：それでお願いします。

確認後に、新しいMacの会話へ最初の依頼を渡します。その後も眼鏡とMacから、同じ相談を続けられます。

### 調べたことを資料にまとめる

> 私：このテーマを調べて、説明用のメモとスライドにまとめたい。
>
> AI：誰に説明する資料で、何を一番伝えたいですか？
>
> 私：同じ部署の人向けです。便利になる点と、導入するときの注意点を伝えたいです。

AIが必要なことを聞き返し、利用できる資料や道具を使って進めます。作業中の報告と、まとまった結果が眼鏡へ戻ります。

文書やスライドを保存する前には、保存先や内容を示して確認を受ける設計です。長い本文を確認しづらいときは、Macなどの大きな画面も使います。利用できる資料や作業は、その人の設定と権限によって変わります。

### 聞き違いや、食い違いがあったとき

音声認識は、周囲の声や話し方によって聞き違えることがあります。確認待ちの返事が話の流れに合わなければ、同意として扱わず、聞き直します。

また、眼鏡でAIの質問を読んだ後にMacから会話を進めると、眼鏡の質問が古くなることがあります。そのときの「はい」を、新しい質問への同意には使いません。最新の内容を眼鏡に表示してから、改めて返事を受けます。

### 終わるとき、通信が切れたとき

終了操作では、眼鏡の録音と、その回の接続を終えます。ただし、Macですでに始まった仕事が取り消されるとは限りません。保存済みの文書などが元に戻るわけでもありません。

通信が切れて返事が見えなくなったときは、同じ依頼の進み具合を確認します。返事がないという理由だけで依頼を送り直し、文書を二重に作ることを避ける設計です。

## コンセプトと設計の理由

「私のAI V2」で実現したかったのは、Macで進めているAIとの相談を、席を離れても続けられることです。

### 相談の続きを、そのまま持ち出す

文書の下書きを作っているとき、途中までのやり取りには大切な情報があります。誰に説明する文書か、何を伝えたいか、どの案を採用したか。別の場所で相談を始めるたびに、それを説明し直すのは手間です。

たとえば、Macで資料の構成を相談した後、外出中に追加の観点を思いついたとします。「さっきの資料に、導入するときの注意点も入れたい」と眼鏡へ話しかけて、同じ相談を続けます。机に戻ったら、その会話を開いて続きを仕上げます。

眼鏡で返事を読むことに加えて、**それまでの相談を踏まえて仕事を続けられること**を重視しました。

### やりたいことを、普通に話す

利用者は「検索」「文書作成」「保存」といった機能を最初に選ぶ必要がありません。「この資料の要点を整理したい」「前の案と比べたい」など、やりたいことを話します。

AIは内容を読み取り、足りないことがあれば聞き返します。人がAIのメニューに合わせるのではなく、AIが相談の流れに合わせることを目指しています。

### 眼鏡とMacに役割を分ける

眼鏡は、声を受け取り、途中経過や返事を表示します。調査や文書作成はMacのAIが担当します。いつも使う資料や道具も、Mac側で利用します。

その間に、どの相談を続けるかを提案する「受付役のAI」を置いています。受付役は相談の続き先を案内し、文書を編集するなどの仕事は行いません。実際の仕事は、選ばれた会話のAIが進めます。

この役割分担により、眼鏡のために調査や文書作成の仕組みを一から作り直す手間を減らしています。

### 確認は、何をするかが変わるところで

同じ相談の続きを話すたびに、続けてよいかを何度も確認すると面倒になります。普通の会話は、そのまま続けられるようにしました。

一方、別の会話へ移るときや新しい会話を始めるときは、実際に使う会話名を画面に出して確認します。文書を保存・編集するときも、対象と内容を示して確認を受けます。

「話し始めること」「相談の続き先を選ぶこと」「文書を変更すること」は、それぞれ別の意思確認として扱います。

### 小さな画面で無理をさせない

眼鏡には、会話名、使っているAI、録音中の状態、途中経過、返事を表示します。同じ報告を何度も描き直して、画面がちらつくことも抑えています。

長い文書の確認や細かな修正にはMacを使えます。眼鏡は、仕事の相談を場所に縛られず続ける入口として考えています。

### この考え方を応用するなら

似た仕組みを考えるときは、まず「どんな仕事の続きを、どこで進めたいか」を決めると整理しやすくなります。相談を引き継ぐこと、道具に役割を分けること、変更前に正確に確認することは、自分の用途を考えるときにも参考になります。

ほかの機種やAIサービスで動かすには、利用できる機能と動作の確認が必要です。

## V1とV2の違い

V1から引き継いだのは、眼鏡からAIへ自然に話しかけることです。V2では、Macで普段使っている会話につなぎ、相談や仕事の続きを進めることを中心にしました。

### 変わったこと

| 観点 | V1 | V2 |
| --- | --- | --- |
| 会話の場所 | 眼鏡向けに用意した会話で進める | Macで普段使っている会話を選んで進める |
| 続け方 | 眼鏡の会話の中で、前のやり取りを踏まえて続ける | 今の相談、別の相談、新しい相談を選び、Macからも続ける |
| 調査や文書作成 | 専用の仕組みで、決められた範囲の作業をする | 選んだMacの会話が使える資料や道具で進める |
| 眼鏡の表示 | 返事を読むことが中心 | 会話名、使っているAI、途中経過、質問、返事を表示する |

V1にも調査や、確認後の保存・編集はありました。V2の特徴は、**普段のMacの相談や作業を、眼鏡から引き継いで続けること**です。

### V1の資料を残す理由

[V1の公開資料](https://github.com/ksuzukigh/rokid-personal-ai)は、最初にどんな仕組みを作り、そこからどう発展させたかを知る資料として残しています。以前の記事やリンクから来た人も、当時の内容を読めます。

V1の説明は「できること」「使い方」「仕組み」の順に案内していました。V2の公開資料も、技術に詳しくない方が利用場面から理解できる順序を基本にしています。

### 資料を使い分けるとき

V1の操作手順や制限は、当時のものです。たとえばV2では、「タップして話す」または「タップして続けて話す」から録音を始めます。現在の使い方はV2の説明を参照してください。

V1には参考コードがありますが、それを使えばV2になるわけではありません。V2は考え方と作るための資料を公開しており、実際に動かしているプログラム一式は含めていません。

## 仕組みをやさしく説明

眼鏡は、MacのAIへ話しかける入口です。調査や文書作成はMacで進め、その返事を眼鏡へ戻します。

![眼鏡で話し、MacのAIが相談や作業を進め、途中経過と返事を眼鏡へ戻す流れ](docs/images/system-overview.svg)

### 声が返事になるまで

1. **眼鏡で話す。** 操作したときだけ録音し、音声をMacへ送ります。
2. **Macで文字にする。** 話した内容を、AIへ渡せる文章に変換します。
3. **相談の続き先を選ぶ。** 受付役のAIが、今の会話を続けるか、別の会話か、新しい会話かを提案します。別の会話や新しい会話では、会話名を確認します。
4. **MacのAIが仕事を進める。** 選ばれた会話で、それまでのやり取りや利用できる資料・道具を使って相談を進めます。
5. **眼鏡で返事を読む。** 途中経過、AIからの質問、最終的な返事を表示します。声で答えると、同じ会話へ戻ります。

### それぞれが担当すること

| 担当 | 役割 |
| --- | --- |
| 眼鏡 | 声を受け取り、会話名や返事を表示する |
| Macの受付 | 登録した眼鏡からの通信かを確認し、依頼や表示の状態を覚えておく |
| 音声を文字にする仕組み | Macの中で文字起こしをする。処理後に録音した音声を削除する |
| 受付役のAI | どの相談を続けるかを案内する。文書を編集する仕事はしない |
| Macの会話のAI | 調べる、考える、文書を作るなど、実際の相談や作業を進める |

Macが使える資料やサービスは、利用者が接続した範囲に限られます。作者の環境では、メモ・資料を保存するObsidianや、Google Driveの文書などを利用しています。誰の環境でも同じ資料を使えるわけではありません。

### 外出先から使うには

眼鏡をインターネットにつなぎ、自宅などにあるMacへ通信を届けます。スマートフォンのテザリングは、眼鏡にスマートフォンの通信を使わせる方法です。

Mac側にも通信を受け取る仕組みが必要です。作者の環境ではCloudflare Tunnelという仕組みを使っています。これで通信を届けることと、接続した眼鏡が本人のものか確かめることは、別に扱います。

### 会話を取り違えないために

Macは、依頼と実際の会話先、送った状態、返ってきた結果を対応させて覚えておきます。通信が途切れても、同じ依頼の結果を探し、むやみに送り直さないためです。

眼鏡に表示した質問も覚えておきます。古い質問への返事を、別の新しい質問への同意として使うことを防ぎます。

### 自分用に作るときの注意

MacにAIアプリがあるだけで、眼鏡から自動的につながるわけではありません。音声を届け、既存の会話へ渡し、結果を取り出す部分の開発が必要です。特に、普段のMacの会話へつなぐ方法は、使っているアプリや版によって調査が必要になります。

## 安心して使うための考え方

声で自然に頼めることと、意図した相手や文書へ正しく届くことを両立させるため、次のように考えています。

### 開いただけでは録音しない

「タップして話す」または「タップして続けて話す」を1回操作すると録音を始めます。録音中であることを表示し、話し終わったときの操作で終了します。最長は60秒です。録音開始のために、さらにもう一度確認させる手順は入れていません。

録音した音声と、文字起こしのための一時音声は、処理後に削除します。失敗や取消の場合も削除を確認する設計です。ただし、**文字にした発言やAIとの会話履歴は別に残ります。** 音声を消すことと、すべての記録を消すことは違います。

### 聞き違いを、そのまま同意にしない

音声を文字にする前に、人の声がある区間を確かめ、無音から誤った文章が生まれることを減らしています。ただし、周囲の人やテレビの声を完全に除けるわけではありません。

確認待ちの返事が文脈に合わないときは、同意と決めつけず、元の依頼を保持して聞き直します。利用者も、会話名や重要な確認内容を画面で確かめることが大切です。

### 相談の続き先を確認する

別の会話へ移るときや、新しい相談を作るときには、実際に使う会話名を画面に表示します。AIがそれらしい名前を説明するだけで送るのではなく、Macが実際の会話先を確かめます。

また、Macから先に相談を進めたために眼鏡の質問が古くなった場合、古い質問への「はい」を新しい質問の承認には使いません。最新の内容を表示します。

### 文書を変更する前に確認する

保存や編集の前には、どの文書へ、何をするかを示して確認を受けます。確認後に対象や本文が変われば、改めて確認します。話し始めるための操作や、会話先への同意を、文書変更の許可には使いません。

送信や公開などを扱う場合にも、この考え方を適用します。ただし、作者のV2で全種類の操作を確認済みという意味ではありません。[実際に確かめた範囲](#確かめたこととまだできると言えないこと)を参照してください。

実行後は、実際の文書や保存先を確かめます。「保存しました」というAIの返事だけで、保存に成功したと判断しないようにしています。

### 返事がないときに、同じ仕事を繰り返さない

通信が切れた場合、依頼が届かなかったのか、届いて仕事が進んでいるのか、その時点ではわからないことがあります。そこで、まず同じ依頼の状態を確かめます。返事がないという理由だけで送り直すと、文書などを二重に作るおそれがあるためです。

エラーが出ても、途中まで変更されていることがあります。実際の保存先も確認します。眼鏡を閉じる操作で、Macで始まった仕事の取消や、保存済み文書の復元が保証されるわけではありません。

### 接続と資料の扱いを決める

本人が登録した眼鏡からだけ利用できるようにし、登録を解除できるようにします。通信を届ける仕組みとは別に、利用者や端末を確認します。

認証情報を公開資料や配布用のファイルへ入れません。資料やサービスの利用範囲も、自分が許可した範囲にします。職場の資料を使う場合は、その職場で認められたAIや保存先、資料の扱いを前提に、自分の用途を検討します。

ここで紹介したのは、作者が確認した条件での設計と対策です。すべての聞き違い、故障、通信の状態に対する保証ではありません。

| テスト資料 | ObsidianやGoogle Driveを接続する場合も、最初は本番と分けた資料・保存先で確認する |

Androidの補助アプリを自作する場合はJDKとAndroid SDK等も必要です。Android一般の仕様だけでRV101の動作を判断せず、Rokidの公開資料とYodaOS実機で確かめます。

#### 独立した会話と、普段のデスクトップ会話

一般的な会話クライアントの出発点は、[Codex App Serverの公式資料](https://learn.chatgpt.com/docs/app-server)です。初期化、会話の作成・再開、入力、イベント、完了状態を扱う接続部を確認します。

作者のV2では、新規会話の初回は会話を作成したApp Server接続、既存デスクトップ会話の続きはデスクトップ側のキュー経路を使っています。2026年10月10日に確認した公式資料には、この既存会話用キューの同じ呼び出し仕様は掲載されていません。一般のApp Serverクライアントだけで、開いているデスクトップ会話へ同様に投入できるとは案内していません。

ここはアプリと版に合わせた調査が必要です。利用できる経路がなければ独立したテスト会話までに留めます。会話履歴ファイルへの直接追記、アカウント認証の抜き取り、無条件の権限拡張で代用しません。この資料はAPIキーの購入や従量課金を前提としていません。選ぶ経路の認証・課金条件は自分の環境で確認します。

#### 登録と、その回の接続

初回の本人確認付き端末登録と、会話ごとの短命な接続を分けます。Mac側で期限・登録解除・失効を管理し、未登録端末を拒否します。トンネル管理用の秘密、端末登録情報、会話ごとの秘密を分離します。

有効な秘密を生成済みAgent、Git、URL、ログへ埋め込みません。「非公開Agent」という表示だけで、生成ファイルの取得が保護されるとは扱いません。AIUIの保存機能も専用の安全な鍵保管庫とは扱わず、保存失敗、破損、紛失、再起動、資源更新、登録解除を実装と端末で確認します。

#### 部品の分け方の例

```text
自分のプロジェクト/
  glasses-agent/       録音・表示・通信・終了
  mac-service/         認証、受付、状態保存、常設起動
  speech/              VAD、文字起こし、一時音声の削除
  conversation-guide/  会話先を提案する受付AI
  conversation-link/   実会話先の照合、送信、状態・結果の読取
  owner-web/           必要なら本人用の大きな表示
  checks/              模擬・Mac・実機それぞれの確認
```

これは役割を分けるための例で、個人用実装のディレクトリを公開したものではありません。受付AIは会話先の提案だけを行い、ファイルやサービスの操作権限を持ちません。本人用Webは長文などの補助表示で、利用開始前の必須メニューにはしません。

### 体験の要求

1. 利用者は操作メニューで分類せず、自然に依頼する。
2. 起動だけでは録音しない。「タップして話す」または「タップして続けて話す」の1回操作で始め、話し終えたら1回操作で終了する。最長60秒。
3. 現在の会話の普通の続きは同じMac会話へ渡す。別会話・新規会話は、実際の送信先名を表示して確認する。
4. 質問と返答、途中経過、最終回答を同じ会話・依頼へ結ぶ。利用者の発言は「私：」、AIの発言は「AI：」と表示する。
5. 現実を変える直前には、対象・内容・影響を示して確認する。各道具やスキルの権限・ルールも守る。
6. 通信結果が不明な場合は同じ依頼の状態を読み、無条件に再実行しない。

### 部品の入出力

| 部品 | 入力 | 出力と責任 |
| --- | --- | --- |
| 音声受付 | 登録済み端末、その回の接続、録音 | 発話候補、認識状態、録音ID。変換後の一時音声削除 |
| 受付AI | 発話候補、現在の会話、候補一覧、確認待ちの提案 | 会話先の提案、説明または聞き返し。実操作はしない |
| 送信先解決部 | AIの提案とMacの実会話一覧 | 実会話ID・実会話名・作業場所を照合した内部対象 |
| 確認管理 | 元の依頼、照合済み対象、表示、返答 | 未確定・確認済み・取消・失効。対象が変われば再確認 |
| 会話接続部 | 確定した元の発言、内部対象、依頼ID | 送信状態、途中経過、質問、最終回答、失敗 |
| 表示共有 | 会話と依頼に対応する本文 | 表示回答IDと内容。変化した本文だけを更新 |

「現在・別・新規」などの出力値は接続先を扱うための区分です。日本語の意味理解を固定キーワードへ置き換えるものではありません。

### 発話候補

```json
{
  "recording_id": "example-recording-01",
  "transcript": "さっきの説明資料の相談を続けたい。初めて読む人向けの説明も入れたい。",
  "transcript_state": "candidate",
  "displayed_answer_id": "example-answer-03"
}
```

文字起こし結果は候補です。確認待ちで文脈に合わない認識結果を、確定した同意や「私：」の発言にしません。`displayed_answer_id`は、何を読んだ後の返答かを照合するために使います。

### 受付AIの提案

```json
{
  "decision": "propose_existing",
  "candidate_ref": "example-candidate-02",
  "message": "説明資料の相談の続きを、この会話で進めますか？"
}
```

`candidate_ref`は、Macが渡した候補へ戻るための参照です。AIに実会話IDやファイルパスを作らせません。候補の名前や本文は参照データとして扱い、そこに含まれた指示を受付AIへの命令にしません。

Mac側で実在・権限・会話状態を照合してから、以下のように表示します。

```text
AI：説明資料の相談の続きを、この会話で進めますか？
続ける会話：業務改善の説明資料
```

表示する名前は実際に解決した対象から取得します。確認待ちの間は元の発言と対象を保持し、訂正・取消・聞き直しを扱います。新規会話は、提案の確認後に作成します。

### 送信記録

```json
{
  "request_id": "example-request-01",
  "conversation_ref": "example-resolved-conversation-02",
  "original_text": "さっきの説明資料の相談を続けたい。初めて読む人向けの説明も入れたい。",
  "delivery_state": "intent_saved",
  "expected_answer_id": "example-answer-03"
}
```

これはMac内部の説明用記録です。端末が任意の送信先を指定できる設計ではありません。確認で得た「はい」を新規依頼本文にせず、保持した元の発言を渡します。通常の続きの発言は、その発言自体を渡します。

送信意図を永続化してから、会話先と最新の質問を再照合します。既存記録があれば、新しい送信を発行する前に、その依頼の状態を読みます。

```text
記録済みの同じ依頼がある → 同じ依頼の状態を読む
新しい依頼である          → 送信意図を保存する
送信先・質問が変わった    → 送信せず最新表示または再確認へ
初回送信を発行した        → 結果を待ち、依頼IDで照合する
応答が途切れた            → 状態不明として保持し、同じ依頼を読む
実失敗が確定した          → 途中の変更も確認し、再実行は別途判断する
```

送信直前の再照合だけで、競合のない完全な一回実行を証明できるわけではありません。受け側の重複抑止や、実変更の側でも確認を維持します。結果不明を自動再送で埋め合わせないことが重要です。

### 途中経過と結果

```json
{
  "request_id": "example-request-01",
  "conversation_ref": "example-resolved-conversation-02",
  "answer_id": "example-answer-04",
  "state": "completed",
  "text": "初めて読む人向けに、最初に業務の流れを説明する案を考えましょう。",
  "model_label": "利用中の実モデル名"
}
```

受信した結果の依頼と会話を照合し、別の仕事の本文を表示しません。`completed`以外の状態を最終成功にしません。同じ本文の再受信で画面を描き直さず、変化した途中経過と最終回答を反映します。

モデル名は、Mac会話の実際の設定から取得します。受付AIのモデルを作業モデルとして表示しません。モデル情報だけの取得失敗なら本文を保ち「モデル確認中」と表示します。

モデル切替を実装する場合は、使用中モデルと明示した標準モデルを分けます。モデルについての評判や比較を切替依頼と誤解せず、利用可能な一覧で解決します。モデル変更で権限を広げません。

### 古い質問への返答

返答には、眼鏡へ表示した回答の識別情報を結びます。Mac側では対象会話の最新ターンと本文も再確認します。

| 条件 | 扱い |
| --- | --- |
| 表示した質問とMacの質問が一致 | 意味を確認し、同じ会話へ返答する |
| MacまたはWeb側で会話が先に進んだ | 古い返答を送らず、最新の内容を表示する |
| 質問の照合ができない | 同意として実行せず、状態を確認する |
| 認識した返事が確認の文脈に合わない | 元の依頼と提案を保持して聞き直す |

### 実変更の確認

文書作成・編集などは、作業を担当するMac会話が、対象・内容・保存先や送信先・影響を示します。確認はその提案だけへ結び、古い確認を再利用しません。

対象や本文が確認後に変わったら再確認します。実行後は文書・セル・サービスの実状態を読み戻します。「実行しました」というAIの返事だけを成功証拠にしません。

### 実装時の合格条件

[再現の手引き](#自分用に作るための進め方)の段階ごとに、正常な往復、取消、曖昧な認識、古い質問、失効、送信応答の欠落、部分失敗、終了を確かめます。認証処理と削除処理は疑似コードだけで済ませず、自分の実装で検証してください。
