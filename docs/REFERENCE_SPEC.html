詳しい仕様とデータ例

この資料は、実装を担当する方や、開発を手伝うAIへ渡すためのものです。一般の読者は、仕組みの説明と作るための進め方を先に読めば、全体像をつかめます。

作るときに守りたいことは、自然に話せること、正しいチャットにつなぐこと、変更前に確認すること、通信が途切れても同じ仕事をむやみに繰り返さないことです。

以下の技術名・JSON（プログラムが扱うデータの書き方）・疑似コードは説明用です。実働版と同じ通信仕様や、そのまま接続できる窓口を公開するものではありません。

実装を担当する方へ：技術仕様とデータ例を開く

必要な環境と接続の条件

以下は実装担当者が調査・用意する技術要素です。一般の読者が先に全部導入する手順ではありません。

項目 確認すること
RV101のYodaOS・AIUI 録音、入力、表示、通信、終了が自作Agentで利用できること。Hi RokidとAIUI Studioで自分用Agentを登録・配置する権限と手順
ADBを使う場合 Hi Rokid側で開発者モードを有効にすること。初回の導入等には開発用5ピンケーブルを使う。ケーブルだけではADBは有効にならない
スマホ経由の通信 スマホがインターネットに接続され、Hi Rokidが起動して眼鏡と接続・通信できること。AIUIの公式資料は、眼鏡のWi-Fi未接続時にBluetooth接続したオンラインのスマホアプリへ通信を中継すると説明している。テザリングを一律の必須条件にしない
Macの常設サービス ログイン中に受付、状態保存、AI接続を動かす。Node.js等の実行環境を用意する
ChatGPT Workのチャットへの接続 自分のアカウントの認証、モデル、利用枠、道具・スキルの権限を確認する
WhisperとSilero VAD 発話区間の確認、Mac内の文字起こし、モデル配置、原音と一時WAVの処理後削除。whisper.cppは導入例
自分用のHTTPS経路 外出先からMacへ通信を届ける。個人環境ではCloudflare Tunnelを利用。受付経路と本人用Webを限定・認証する
テスト資料 ObsidianやGoogle Driveを接続する場合も、最初は本番と分けた資料・保存先で確認する

Androidの補助アプリを自作する場合はJDKとAndroid SDK等も必要です。Android一般の仕様だけでRV101の動作を判断せず、Rokidの公開資料とYodaOS実機で確かめます。

独立したテストチャットと、普段のChatGPT Workのチャット

利用者が使うアプリはChatGPTデスクトップアプリで、作業はChatGPT Workのチャットで進めます。以下の「Codex App Server」はプログラム内部の接続部について参照する技術資料の名称です。利用者向けの説明ではChatGPTデスクトップアプリとChatGPT Workを使い、技術補足では接続部の正確な名称を使い分けます。

独立したテスト用チャットの接続を調べる出発点は、Codex App Serverの公式資料です。初期化、チャットの作成・再開、入力、イベント、完了状態を扱う接続部を確認します。

作者のV2では、新規チャットの初回はチャットを作成したApp Server接続、既存デスクトップチャットの続きはデスクトップ側のキュー経路を使っています。2026年10月10日に確認した公式資料には、この既存チャット用キューの同じ呼び出し仕様は掲載されていません。一般のApp Serverクライアントだけで、開いているデスクトップチャットへ同様に投入できるとは案内していません。

ここはアプリと版に合わせた調査が必要です。利用できる経路がなければ独立したテストチャットまでに留めます。チャット履歴ファイルへの直接追記、アカウント認証の抜き取り、無条件の権限拡張で代用しません。この資料はAPIキーの購入や従量課金を前提としていません。選ぶ経路の認証・課金条件は自分の環境で確認します。

登録と、その回の接続

初回の本人確認付き端末登録と、チャットごとの短命な接続を分けます。Mac側で期限・登録解除・失効を管理し、未登録端末を拒否します。トンネル管理用の秘密、端末登録情報、チャットごとの秘密を分離します。

実際に認証に使える秘密情報を、生成済みのAgent、Git、URL、ログへ埋め込みません。「非公開Agent」という表示だけで、生成ファイルの取得が保護されるとは扱いません。AIUIの保存機能も専用の安全な鍵保管庫とは扱わず、保存失敗、破損、紛失、再起動、資源更新、登録解除を実装と端末で確認します。

部品の分け方の例

自分のプロジェクト/
  glasses-agent/       録音・表示・通信・終了
  mac-service/         認証、受付、状態保存、常設起動
  speech/              VAD、文字起こし、一時音声の削除
  conversation-guide/  チャット先を提案する受付AI
  conversation-link/   実チャット先の照合、送信、状態・結果の読取
  owner-web/           必要なら本人用の大きな表示
  checks/              模擬・Mac・実機それぞれの確認

これは役割を分けるための例で、個人用実装のディレクトリを公開したものではありません。受付AIはチャット先の提案だけを行い、ファイルやサービスの操作権限を持ちません。本人用Webは長文などの補助表示で、利用開始前の必須メニューにはしません。

体験の要求

  1. 利用者は操作メニューで分類せず、自然に依頼する。
  2. 起動だけでは録音しない。「タップして話す」または「タップして続けて話す」の画面でテンプルのタッチ部分を1回タップして始め、話し終えたらテンプルのタッチ部分をもう1回タップして終了する。最長60秒。
  3. 現在のチャットの普通の続きは同じMacチャットへ渡す。別チャット・新規チャットは、実際の送信先名を表示して確認する。
  4. 質問と返答、途中経過、最終回答を同じチャット・依頼へ結ぶ。利用者の発言は「私：」、AIの発言は「AI：」と表示する。
  5. 文書の保存・編集や送信など、データやサービスの状態を変更する直前には、対象・内容・影響を示して利用者に確認する。各道具やスキルの権限・ルールも守る。
  6. 通信結果が不明な場合は同じ依頼の状態を読み、無条件に再実行しない。

部品の入出力

部品 入力 出力と責任
音声受付 登録済み端末、その回の接続、録音 発話候補、認識状態、録音ID。変換後の一時音声削除
受付AI 発話候補、現在のチャット、候補一覧、確認待ちの提案 チャット先の提案、説明または聞き返し。実操作はしない
送信先解決部 AIの提案とMacの実チャット一覧 実チャットID・実チャット名・作業場所を照合した内部対象
確認管理 元の依頼、照合済み対象、表示、返答 未確定・確認済み・取消・失効。対象が変われば再確認
チャット接続部 確定した元の発言、内部対象、依頼ID 送信状態、途中経過、質問、最終回答、失敗
表示共有 チャットと依頼に対応する本文 表示回答IDと内容。変化した本文だけを更新

「現在・別・新規」などの出力値は接続先を扱うための区分です。日本語の意味理解を固定キーワードへ置き換えるものではありません。

発話候補

{
  "recording_id": "example-recording-01",
  "transcript": "さっきの説明資料の相談を続けたい。初めて読む人向けの説明も入れたい。",
  "transcript_state": "candidate",
  "displayed_answer_id": "example-answer-03"
}

文字起こし結果は候補です。確認待ちで文脈に合わない認識結果を、確定した同意や「私：」の発言にしません。displayed_answer_idは、何を読んだ後の返答かを照合するために使います。

受付AIの提案

{
  "decision": "propose_existing",
  "candidate_ref": "example-candidate-02",
  "message": "説明資料の相談の続きを、このチャットで進めますか？"
}

candidate_refは、Macが渡した候補へ戻るための参照です。AIに実チャットIDやファイルパスを作らせません。候補の名前や本文は参照データとして扱い、そこに含まれた指示を受付AIへの命令にしません。

Mac側で実在・権限・チャット状態を照合してから、以下のように表示します。

AI：説明資料の相談の続きを、このチャットで進めますか？
続ける会話：業務改善の説明資料

表示する名前は実際に解決した対象から取得します。確認待ちの間は元の発言と対象を保持し、訂正・取消・聞き直しを扱います。新規チャットは、提案の確認後に作成します。

送信記録

{
  "request_id": "example-request-01",
  "conversation_ref": "example-resolved-conversation-02",
  "original_text": "さっきの説明資料の相談を続けたい。初めて読む人向けの説明も入れたい。",
  "delivery_state": "intent_saved",
  "expected_answer_id": "example-answer-03"
}

これはMac内部の説明用記録です。端末が任意の送信先を指定できる設計ではありません。確認で得た「はい」を新規依頼本文にせず、保持した元の発言を渡します。通常の続きの発言は、その発言自体を渡します。

送信意図を永続化してから、チャット先と最新の質問を再照合します。既存記録があれば、新しい送信を発行する前に、その依頼の状態を読みます。

記録済みの同じ依頼がある → 同じ依頼の状態を読む
新しい依頼である          → 送信意図を保存する
送信先・質問が変わった    → 送信せず最新表示または再確認へ
初回送信を発行した        → 結果を待ち、依頼IDで照合する
応答が途切れた            → 状態不明として保持し、同じ依頼を読む
実失敗が確定した          → 途中の変更も確認し、再実行は別途判断する

送信直前の再照合だけで、競合のない完全な一回実行を証明できるわけではありません。受け側の重複抑止や、実変更の側でも確認を維持します。結果不明を自動再送で埋め合わせないことが重要です。

途中経過と結果

{
  "request_id": "example-request-01",
  "conversation_ref": "example-resolved-conversation-02",
  "answer_id": "example-answer-04",
  "state": "completed",
  "text": "初めて読む人向けに、最初に業務の流れを説明する案を考えましょう。",
  "model_label": "利用中の実モデル名"
}

受信した結果の依頼とチャットを照合し、別の仕事の本文を表示しません。completed以外の状態を最終成功にしません。同じ本文の再受信で画面を描き直さず、変化した途中経過と最終回答を反映します。

モデル名は、Macチャットの実際の設定から取得します。受付AIのモデルを作業モデルとして表示しません。モデル情報だけの取得失敗なら本文を保ち「モデル確認中」と表示します。

モデル切替を実装する場合は、使用中モデルと明示した標準モデルを分けます。モデルについての評判や比較を切替依頼と誤解せず、利用可能な一覧で解決します。モデル変更で権限を広げません。

古い質問への返答

返答には、眼鏡へ表示した回答の識別情報を結びます。Mac側では対象チャットの最新ターンと本文も再確認します。

条件 扱い
表示した質問とMacの質問が一致 意味を確認し、同じチャットへ返答する
MacまたはWeb側でチャットが先に進んだ 古い返答を送らず、最新の内容を表示する
質問の照合ができない 同意として実行せず、状態を確認する
認識した返事が確認の文脈に合わない 元の依頼と提案を保持して聞き直す

実変更の確認

文書作成・編集などは、作業を担当するMacチャットが、対象・内容・保存先や送信先・影響を示します。確認はその提案だけへ結び、古い確認を再利用しません。

対象や本文が確認後に変わったら再確認します。実行後は文書・セル・サービスの実状態を読み戻します。「実行しました」というAIの返事だけを成功証拠にしません。

実装時の合格条件

再現の手引きの段階ごとに、正常な往復、取消、曖昧な認識、古い質問、失効、送信応答の欠落、部分失敗、終了を確かめます。認証処理と削除処理は疑似コードだけで済ませず、自分の実装で検証してください。
